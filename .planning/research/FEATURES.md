# Исследование функций MealPlan

**Область:** русскоязычный гостевой планировщик питания с бюджетом, КБЖУ, домашними запасами и покупками.  
**Дата:** 25 октября 2026 года.  
**Основание:** PRD, PROJECT, OPEN_QUESTIONS, AGENTS и mealplan-domain.  
**Уверенность:** высокая в трассировке документированных требований; средняя в оценках сложности и порядка реализации; низкая в неподтверждённых рыночных ожиданиях. Внешнее исследование конкурентов не проводилось. Документ не подтверждает реализацию или прохождение тестов.

## Границы исследования и приоритетов

Это карта функций по утверждённому направлению проекта, а не предложение сократить MVP до нескольких экранов. Весь P0-01–P0-16 входит в v1, включая дополнения подробного frontend-ТЗ §12.1: 1–7 дней, разнообразие, 3–4 варианта, пересборку с сохранением предыдущего, день/неделю и табы категорий покупок. P1 начинается после приёмки всего P0. P2 разрешён только отдельным запросом. Обозначения P0/P1/P2 здесь совпадают с проектом: шкала приоритетов из универсального шаблона намеренно не применяется. [S1 §3; S2; S3]

Под «базовыми» понимаются функции, необходимые для заявленного пользовательского пути MealPlan. Это вывод из PRD, а не доказательство наличия функции у всех конкурентов. «Отличительные» обозначают ценность выбранной комбинации возможностей; конкурентное превосходство требует отдельной проверки. Наличие функции в отличительных возможностях не делает обязательный P0 необязательным.

## Зависимости функций

В схеме стрелка означает «необходимо для следующей возможности»; это рекомендация порядка, а не новый roadmap.

```text
Проверенные Product/Recipe + ID + база единиц/порций/цен
  → нормализация + масштабирование + расчёт КБЖУ/стоимости
  → агрегация потребностей + однократное покрытие запасами
  → оценка закупки и проверка бюджета кандидата
  → генерация допустимого плана и допустимых альтернатив

Каркас + черновик мастера + валидированные настройки
  → генерация/отмена/повтор/диагностика
  → 3–4 варианта + активный план + сохраняемая пересборка
  → меню день/неделя + рецепт + замена/удаление/добавление
  → пересчёт зависимых данных
  → покупки + категории/табы + ручные правки/отметки
  → текстовый обмен + PDF из актуального списка

Поиск продуктов + pantry CRUD
  → настройки генерации и приоритет expiresSoon
  → покрытие потребностей и актуальные покупки

Порции конкретного вхождения блюда
  → ингредиенты + КБЖУ + полная стоимость
  → повторная агрегация/покрытие + бюджет + покупки + экспорт

Общие состояния + доступность + адаптивность + сохранение данных
  → все пользовательские срезы с начала разработки
```

### Практические следствия для планирования

- Сначала согласовать базу денег, нормы и порций и подготовить проверяемые данные. Иначе генератор, дельты замены и бюджет UI будут считать разные величины. Q-03/Q-04/Q-05/Q-14/Q-16 — ворота соответствующих функций, а не задача косметической полировки.
- Варианты требуют коллекции результатов и выбранного плана с самого начала контрактов. Прикрепить их в конце к состоянию одного меню приведёт к переделке покупок, правок и хранения. Q-06 нельзя решить случайным индексом массива.
- Pantry-вычет нужен внутри оценки кандидата, если итоговый лимит будет контролировать закупку. Делать его только на экране покупок опасно: генерация и UI разойдутся. Выбор базы лимита остаётся Q-04.
- Для масштабирования важен ID вхождения блюда, поскольку один recipeId может встречаться несколько раз. Выбор точного контекста и применение правки открыты в Q-05.
- Ручной товар, ручная правка автоматически рассчитанной строки и чекбокс покупки имеют разные последствия. Нужна явная политика Q-09 до интеграционной приёмки покупок.
- PDF зависит от корректного актуального списка, но кириллицу, длинные строки и многостраничность стоит проверить ранним техническим прототипом. Это исследовательская рекомендация, не добавление функции.
- Каталог P1, аккаунты и серверная синхронизация не блокируют P0. Качественные данные рецептов, напротив, блокируют достоверный результат уже в v1.

## Определение релиза

### v1: весь обязательный P0

- [ ] Гостевой сквозной путь: приветствие/быстрый старт → четыре шага с устойчивым черновиком → реальная генерация и восстановление после ошибки.
- [ ] Параметры 1–10 людей, 1–7 дней, бюджет/время, цель/норма в пределах разрешённых требований, ограничения, продукты дома и разнообразие.
- [ ] 3–4 варианта и пересборка с сохранением предыдущего; меню день/неделя, сводки и оценочные цены.
- [ ] Рецепт с ингредиентами/шагами/КБЖУ/ценами и порциями; допустимая замена, удаление и добавление блюда.
- [ ] Количественный холодильник, приоритет expiresSoon и единые расчёты потребности/покрытия/закупки.

### P1: только после приёмки P0

Полный перечень из PRD сохраняется без повышения приоритета:

- Избранные рецепты/недели, история, повтор недели, календарь и выбор дат.
- График калорий/норма; дополнительные нутриенты и граммы/% только при наличии данных.
- Вход/регистрация/сброс пароля/Google через настроенный Firebase Auth, перенос гостевых данных.

- «Можно приготовить» с корректно определённым процентом совпадения; собственный продукт с КБЖУ на 100 г.

Это граница будущего объёма, а не разрешение автоматически начинать P1 до P0. История приготовленного и статистика экономии — разные функции: экономия как историческая статистика остаётся P2 по C-05. [S1 §3.2,6; S3]

Семья и общий список в реальном времени, разные ограничения членов семьи, статистика экономии, персонаж-помощник, перенос блюд между днями, собственные рецепты, сохранённые приёмы пищи, сканер штрихкодов. Не связывать архитектуру готовности v1 с наличием этих модулей. [S1 §3.3]

### Рекомендация порядка функциональных срезов

1. **Основание корректности:** решения расчётных ворот, словарь продуктов, единицы, порции, КБЖУ/цены, агрегация и pantry-покрытие; параллельно общий доступный каркас и состояния.
2. **Первое меню:** устойчивый мастер, настройки, гостевой путь, детерминированная генерация с отменой/отказами; варианты, разнообразие и активный план закладываются в контракты этого среза.
3. **Управление планом:** день/неделя, рецепт, порции, замена/удаление/добавление, пересборка и согласованный пересчёт.
4. **Практическая закупка:** полный pantry UI, связь с меню, покупки/категории/табы, ручные действия, текстовый обмен и PDF.
5. **Приёмка P0:** сквозные и граничные сценарии, данные достаточного качества, PDF/адаптивность/доступность, production build. Проверки добавляются при разработке каждого среза; заключительный этап не заменяет их.

Это аналитическая рекомендация для roadmap. Неизвестные Q-03–Q-08/Q-14/Q-16 требуют отдельного исследования перед соответствующей реализацией; повторно выбирать уже определённые гостевой режим, дни, PDF или приоритеты не нужно.
