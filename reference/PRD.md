## 2. Цель, аудитория и результат

MealPlan — адаптивное веб-приложение SPA для автоматизированного планирования питания с учётом бюджета, пищевых ограничений, домашних запасов и КБЖУ. Ценность продукта — единый работающий путь от параметров до меню, рецепта и списка покупок. [F с.1; R §1–4]

Задачи пользователя:

- Быстро решить, что готовить в ближайшие дни, без ручного составления всего рациона.
- Увидеть расчёт стоимости и ограничения бюджета до покупки.
- Рассчитать КБЖУ по структурированным данным продуктов.
- Использовать имеющиеся продукты, особенно скоро портящиеся, и покупать только недостающее.
- Получить объединённый список по отделам магазина и читаемый PDF для печати или передачи.

Аудитория R: студенты, молодые семьи, люди, следящие за питанием, занятые профессионалы. F приводит результаты опроса N=50: 68% — студенты 18–24 лет, 78% живут не одни, 64% учатся или совмещают учёбу с работой, 67% следят за питанием, 68% считают бюджет важным, 66% почти не планируют питание. Это данные исходного ТЗ, независимо не проверялись. Продуктовое следствие F: телефон — основное устройство, минимум настроек, интерфейс без необходимости читать инструкцию.

Успех MVP определяется сквозными критериями §14, а не числом отдельных экранов. Источники не задают метрик удержания, конверсии или количественного снижения пищевых отходов. Указания F на ноябрь–декабрь и защиту — исходные ориентиры команды, не новый календарный план.

### 3.2 P1 — только после удовлетворения P0

- PNG 1080×1920, предпросмотр и передача файла через Web Share при поддержке.
- Режим готовки с шагами, таймерами, звуком/вибрацией и Wake Lock при поддержке.
- Профиль, персональная норма КБЖУ, сохранённые предпочтения и параметры по умолчанию.
- Избранные рецепты и недели, история, повтор недели; календарь с выбором даты и переходом между неделями.
- График калорий по дням и линия нормы; дополнительные нутриенты и переключатель «граммы / %», только при наличии данных.
- Вход/регистрация, сброс пароля, Google через Firebase Auth; перенос гостевых данных в аккаунт.
- Готовые планы команды на приветствии и в сохранённом: «Использовать» переносит настройки в мастер.
- Баннер заполнения профиля на меню при отсутствии нормы, скрываемый на 7 дней.
- «Можно приготовить» в холодильнике: рецепты, процент совпадения, сортировка по нему, переход к рецепту.
- Собственный продукт при отсутствии в поиске: название, вес, КБЖУ на 100 г.
- Каталог `/recipes`: поиск, фильтры по типу, кухне, времени, «Популярное».
- Единый поиск и степпер порций непосредственно в карточке меню.

Источники: F §3, §5.6, §5.10–5.12, §12.1. Статистика приготовленных блюд описана в `/saved`; статистика экономии одновременно названа P2 — см. C-05.

### 3.3 P2 и исключённые интеграции

P2 не разрабатывать без отдельного запроса: семья и общий список в реальном времени, разные ограничения членов семьи, статистика экономии, персонаж-помощник, перенос карточек между днями, собственные рецепты, сохранённые приёмы пищи, сканер штрихкодов. [F §3, §12–13; A]

В текущий объём не входят интеграции магазинов, акций и доставки, КБЖУ по фотографии, партнёрские планы блогеров/тренеров/нутрициологов. Примеры Croopa и рекламные «250+ рецептов» в I не означают обязательства реализовать доставку, партнёрства или такой объём каталога. Обязательная регистрация исключена: MVP работает гостем. Платные LLM/API и платные облачные сервисы не являются зависимостью продукта. [F §3, §12.2; A §13]

## 5. Подробные требования к P0-экранам

### 5.1 Приветствие

Заголовок «Меню на неделю за пару минут» и подзаголовок об учёте бюджета, КБЖУ и домашних продуктов — тексты-заглушки из F; финальный текст дизайнера неизвестен. Статичный блок из трёх шагов: «Настройки → Меню → Покупки».

«Составить меню» открывает мастер. «Меню за 1 клик» запускает генерацию с последними сохранёнными настройками; при их отсутствии — 2 человека, 3 000 ₽, без ограничений, до 30 минут. Дополнение задаёт 7 дней по умолчанию. Цель мастера по умолчанию — поддержание веса; дефолт разнообразия для быстрого старта явно не задан, Q-02. Ссылка входа — P1. [F с.3–4,16]

### 5.2 Мастер

Общее: «Шаг N из 4», прогресс, закреплённая кнопка «Далее», «Назад». С первого шага «Назад» ведёт на `/`, при введённых данных требуется подтверждение. На шагах 3 и 4 есть «Пропустить». Значения переживают переходы между шагами и перезагрузку страницы. [F с.4–5]

| Шаг | Поля и поведение |
|---|---|
| 1. Для кого | Люди: степпер 1–10, по умолчанию 2, чипы 1 / 2 / 4+. Цель: поддержание веса (по умолчанию), похудение, набор массы. По F §12.1 здесь же дни: 1–7, по умолчанию 7; V показывает дни на шаге 2 — C-02 |
| 1. Норма | Раскрываемая мини-форма: пол, возраст, рост, вес, активность; результат сервиса и «Использовать», возможность ручного ввода. Если не рассчитана — средняя норма выбранной цели. Приоритет и сами значения/формулы не определены, C-04, Q-03 |
| 2. Бюджет и время | Числовое поле ₽ и синхронный слайдер 1 000–15 000 ₽ с шагом 100; дефолт 3 000 ₽. Ввод только цифр, минимум поля 500 ₽. Время: до 15 / до 30 (дефолт) / до 60 минут / любое |
| 2. Разнообразие | «Одно и то же каждый день» / «Среднее» / «Каждый день разное»; значения `same`, `medium`, `max`. Дополнение F §12.1, P0 |
| 3. Ограничения | Мультивыбор «Без рыбы», «Без глютена», «Без лактозы», «Вегетарианство», «Халяль». «Не люблю»: теги с подсказкой продуктов, Enter/запятая добавляют, крестик удаляет |
| 4. Что есть дома | Поиск с подсказкой и добавлением; количество и единица необязательны. Чипы: яйца, курица, помидоры, творог, рис, картофель. Строка: название, количество, «Скоро испортится», удаление. «Составить меню» запускает генерацию; «Пропустить» запускает без продуктов этого шага |

Подсказка бюджета F: бюджет / люди / 7. При выборе другого числа дней формула требует уточнения, Q-01. Текст «≈ 214 ₽» — пример для 3 000 / 2 / 7, не константа. Поведение чипа «4+», верхняя граница ручного бюджета, обработка уже сохранённых ограничений/запасов при пропуске не заданы, Q-02/Q-07/Q-11.

### 5.3 Генерация

Полноэкранная анимация со сменой строк примерно раз в 2 секунды: «Подбираю блюда…», «Считаю бюджет…», «Проверяю КБЖУ…», «Собираю список покупок…». Это сопровождение реальной операции, не доказательство завершения отдельных вычислительных стадий.

Вызывается `generateMenu(settings)`, успех открывает `/menu`. P0-дополнение требует 3–4 варианта. «Отмена» прерывает запрос и возвращает на предыдущий экран. Ошибка или таймаут 30 секунд: понятный текст, «Повторить», «Изменить настройки» с сохранёнными значениями. `BUDGET_TOO_LOW` сообщает, для скольких людей и при каких ограничениях бюджета недостаточно; «Изменить бюджет» открывает шаг 2. Минимум «≈ X ₽» допустим только при обоснованном расчёте, способ его получения не определён, Q-08. `NO_RECIPES_FOUND` и `TIMEOUT` — предусмотренные коды; точный текст первого не задан. [F с.6,13,15]

### 5.4 Меню

- Заголовок и даты периода; бюджет «расчёт / лимит», прогресс, «осталось X ₽»; средние ккал в день относительно нормы. При превышении бюджета — красный индикатор, иконка и текст. Сам факт наличия красного состояния не разрешает генератору молча нарушать бюджет.
- Выбор «Вариант N из M», стрелки и сравнение стоимости. «Пересобрать» запускает новую генерацию с теми же параметрами, предыдущий вариант остаётся доступен. Как много вариантов хранить и как переключать состояние правок — Q-06.
- Меню «⋯»: составить заново с подтверждением, изменить настройки, экспорт; сохранить неделю — P1. Различие сброса «Составить заново» и накопления «Пересобрать» — C-01/Q-06.
- На телефоне режимы «Текущий день / Вся неделя» и табы дней с выделением сегодняшнего дня; компактный обзор всей недели. На десктопе сетка 7 колонок × 4 строки: завтрак, обед, ужин, перекус. При периоде менее 7 дней состав сетки не уточнён, Q-01.
- Карточка: фото 4:3, название, цветной текстовый бейдж типа приёма пищи, время, ккал, цена порции, признак использования запасов. Тап открывает рецепт.
- «Заменить» открывает bottom sheet с 3–5 подходящими альтернативами; у каждой разница цены и ккал. Выбор заменяет блюдо и обновляет зависимые данные. «Убрать из меню» освобождает слот; «+ Добавить блюдо» открывает тот же механизм выбора. Избранное — P1; полный каталог для базовой замены P0 не обязателен.
- Сводка дня: Ккал / Б / Ж / У «значение из нормы», стоимость дня. Цвет обычный до нормы, акцент при выполнении, предупреждение при превышении более 10%; смысл дублируется текстом. Единица сравнения семейных значений с нормой на человека требует уточнения Q-04.
- Закреплённая кнопка «Список покупок · N товаров». Пересчёт после правок — сразу, оптимистично, затем подтверждение адаптера; ошибка не должна оставлять ложный успешный результат.
- Внизу — подпись об ориентировочных ценах; КБЖУ не представляется медицинской рекомендацией.

Состояния: skeleton-карточки; «Меню ещё не составлено» с кнопкой старта; ошибка и повтор. График калорий, дата-календарь и степпер порций на карточке — P1. [F с.6–7,15–18]

### 5.5 Рецепт

Шапка: фото, название, время, цена порции, возврат назад. Порции ×0,5 / ×1 / ×2, исходно как в меню: пересчитываются количества, КБЖУ и стоимость. Четыре показателя КБЖУ на порцию, раскрываемый «Состав» с вкладом ингредиентов. Список ингредиентов с количествами, ценами из дополнения §12.1 и отметками «есть дома». Частичный запас не означает полного покрытия количества.

Нумерованные текстовые шаги, необязательные фотографии. «Заменить в меню» открывает альтернативы. Избранное и «Начать готовить» — P1, хотя кнопки нарисованы на V с.3. Состояния: skeleton; неизвестный рецепт — «Такого рецепта нет» и «К меню»; применимые ошибки с повтором. Изменение порций должно согласованно отражаться в зависимых расчётах по A/D; точная семантика «на порцию», семейных порций и выбора конкретного вхождения рецепта — Q-04/Q-05. [F с.7–8,16]

### 5.6 Покупки

Шапка: «N товаров · ≈ S ₽», прогресс «куплено K из N». Группы по порядку: овощи и фрукты → мясо и рыба → молочное → бакалея → хлеб → прочее. Каждая сворачивается, имеет счётчик купленного/всего. Дополнительно горизонтальные табы с иконками: «Все», «Овощи», «Фрукты», «Мясо», «Молочка»; V показывает и «Бакалея». Привязка раздельных табов овощей/фруктов к общей группе — Q-12.

Строка: чекбокс, название, суммарное недостающее количество, цена. Купленный товар зачёркивается и уходит вниз своей группы. «Из N блюд» раскрывает источники. Раздел «Уже есть дома» внизу свёрнут и показывает покрытые запасами продукты и их оценочную стоимость. Частичное покрытие сохраняет недостающую часть в покупках.

Ручное добавление: название, количество, отдел. Тап по числу меняет количество; свайп влево удаляет. Экспорт открывает модальное окно. «Поделиться» передаёт текст через Web Share API, при отсутствии поддержки копирует в буфер. Меню «⋯»: сбросить отметки, показать только нужное, скрыв купленное. Правила сочетания ручных правок с повторной агрегацией, цен ручных позиций и сохранения чекбоксов — Q-09.

Нет меню — «Сначала составьте меню». Всё куплено — поздравление и «Новое меню». Применимы загрузка и ошибка с повтором. Совместный список в реальном времени — P2. [F с.8–9,18; A/D]

### 5.7 Холодильник / продукты дома

Поиск по базе и добавление, популярные чипы, список с правкой количества, переключателем «Скоро испортится» и удалением. Пустое состояние: «Добавьте, что есть дома, и мы не купим лишнего». «Составить меню из остатков» запускает генерацию с приоритетом скоро портящихся продуктов на ближайшие 1–2 дня. Подсказка F «Эти продукты не попадут в список покупок» трактуется количественно: только реально покрытая часть исключается. [F с.10; A/D]

F отдельно требует баннер после изменения запасов при существующем меню: «Пересчитать меню и список?» — «Пересчитать» / «Позже». Это противоречит немедленному пересчёту A/D; в PRD зафиксировано обязательство не показывать устаревшие покупки как актуальные, но поведение баннера остаётся неразрешённым C-03. Создание нового плана из остатков и пересчёт покупок существующего плана — разные операции; источник не определяет, должен ли второй менять блюда.

«Можно приготовить» с процентами и создание своего продукта относятся к P1, персонаж — P2, несмотря на их наличие на V с.6. В P0 не требуются реальные сроки годности и автоматическое списание по приготовлению: задан только флаг, правила списания не описаны, Q-10.

### 5.8 Экспорт PDF

Модальное окно с закрытием, PDF по умолчанию, живым превью, переключателями: группировать по отделам, показывать цены, показывать количество, пустые чекбоксы для печати. Опция количества обязательна по F, хотя отсутствует на V с.5. «Скачать» формирует файл вида `shopping-list_2026-10-06.pdf`; значение даты в имени требует согласования Q-13.

PDF: A4, портрет, логотип из конфига, дата, итоговая сумма, иконки отделов, чекбоксы. Длинный список переносится по страницам без разрыва строки товара. Русские символы читаемы. Технология F: скрытый шаблон, html2canvas и jsPDF; перед рендером дождаться шрифтов (`document.fonts.ready`) и изображений. Во время работы — спиннер; при ошибке «Не удалось создать файл. Повторить». Макет с PNG не делает PNG частью P0.

Объём экспорта при скрытых/купленных/ручных позициях не установлен, Q-13. PDF обязан соответствовать выбранным опциям и данным, а не статическому примеру. [F с.9–10]

## 6. P1-экраны и P2-помощник

### 6.1 Режим готовки

Полноэкранные шаги с прогрессом «Шаг N из M», крупным текстом от 20 px, фото при наличии. Закрытие с подтверждением. Назад/дальше и свайпы. Таймер, если задан у шага: старт, пауза, сброс, звук и вибрация по завершении; продолжает работать при переходе между шагами. Wake Lock при поддержке браузера. Последний шаг «Готово!» закрывает режим и отмечает блюдо приготовленным для статистики. [F с.8]

### 6.2 Профиль

Пол, возраст, рост, вес, активность; рассчитанная норма с ручной корректировкой. Сохраняемые ограничения, диеты, нелюбимые продукты; бюджет, люди и время по умолчанию. «Сохранить» активно при изменениях, «Выйти». Семья — P2. Формула нормы и валидационные диапазоны не заданы. [F с.10–11]

### 6.3 Избранное, история, каталог

`/saved`: вкладки «Избранные недели», «История», «Статистика». Карточка недели: даты, стоимость, средние ккал, 3–4 блюда; «Повторить» создаёт новую неделю, удаление с подтверждением. Счётчик приготовленных блюд предусмотрен, статистика экономии имеет конфликт приоритетов C-05. Шаблоны команды подставляют настройки в мастер. `/recipes` добавлен в F §12.1 как P1; фильтры и поиск описаны в §3.2 этого PRD.

### 6.4 Аутентификация

Email/пароль, регистрация, восстановление, Google/Firebase Auth. До входа данные локальны; предложение войти мягкое, без блокировки базового сценария. После входа гостевые данные переносятся в аккаунт. Правила конфликтов при переносе не описаны, Q-15. Firebase допустим после настройки; платные зависимости не вводятся автоматически. [F с.11; A]

### 6.5 PNG и персонаж

PNG P1: 1080×1920, градиент, иконки продуктов, аккуратный шрифт; при переполнении первые позиции и «и ещё N товаров». Web Share с файлом при поддержке, иначе скачивание. Порог и отбор позиций неизвестны.

Персонаж P2: F рекомендует Хладика, но окончательный выбор оставлен команде. Альтернативы: Копейка, Авокадыч, Колобок, овощная команда. F §13 описывает заменяемый компонент с `idle`, `wave`, `thinking`, `happy`, `worried`, `sleeping`, `celebrate`, `error`; SVG/Lottie до 100 КБ на файл либо WebP; конфиг имени и ресурсов, словарь реплик, 2–3 варианта, русский язык на «ты». Реплика до 6 секунд или до тапа, не чаще одной на экран, без перекрытия действий. Отключение в профиле, уважение reduced motion, декоративное изображение с пустым alt, доступный текст, работоспособность без ресурса. Это описание будущей функции, не разрешение реализовать её в P0.

### 7.1 Границы системы

Подтверждённое направление: React + строгий TypeScript, SPA, Tailwind CSS; Vite, React Router — предпочтительный инструментарий. Zustand и TanStack Query — по необходимости, не обязательные зависимости. Доменные вычисления — чистые тестируемые TypeScript-функции вне React. UI не содержит отдельных копий расчётов. [F §8–9; A/D]

Сначала `api/` и локальные mock-адаптеры с реальными детерминированными вычислениями; `src/mocks` содержит исходные тестовые данные. Замена на настоящий backend не должна требовать переделки экранов. Firebase Firestore/Auth — направление исходных документов, но подключение только при наличии конфигурации и необходимости. Место серверной генерации (Cloud Functions / сервер) не выбрано. Платный LLM для генерации не используется. [F с.12–15; A]

Данные внешнего адаптера валидируются. Работа с ошибками, отменой и подтверждением оптимистичных изменений необходима, но транспорт и схема версионирования запросов не определены.

## 8. Генерация меню и ограничения

Требуется детерминированный, воспроизводимый алгоритм ограниченной оптимизации. Исходники не определяют конкретный solver, веса критериев или способ перебора; ниже — обязательные этапы и инварианты, а не утверждение о существующей реализации. [R §4.1; A/D]

1. Получить валидированные настройки, каталог и доступные запасы: люди, дни, бюджет, цель/норма, ограничения, время, разнообразие.
2. Отфильтровать недопустимые рецепты по аллергиям, явным исключениям и пищевым ограничениям, допустимому типу приёма пищи и выбранному времени. Не считать рецепт безопасным, если данные об ингредиентах/ограничениях не позволяют это подтвердить. Аллергии не ослабляются ради результата.
3. Рассчитать порции для выбранного числа людей и каждого слота без двойного умножения. В исходной сетке четыре типа приёма пищи. Число дней по умолчанию 7, допускается 1–7.
4. Подбирать сочетания с учётом бюджета, целевых КБЖУ и разнообразия; предпочитать имеющиеся продукты, особенно `expiresSoon` в первые 1–2 дня. Приоритет запасов не отменяет жёстких ограничений.
5. Для каждого кандидата агрегировать ингредиенты всего периода, однократно распределить покрытие запасами и вычислить недостающее. Оценивать стоимость по тем же функциям, что использует UI покупок.
6. Проверить весь план на жёсткие ограничения. Не выдавать превышение бюджета как обычный успешный результат; при невозможности — объяснение. Базу бюджетного ограничения ещё нужно определить: вся стоимость или дополнительные покупки, Q-04.
7. Сформировать предусмотренные 3–4 варианта и согласованные производные: дни, КБЖУ, цены, покупки, признаки использования запасов. При недостатке допустимых отличающихся вариантов не подделывать разнообразие, правило ответа не определено Q-06.
8. При замене, удалении, добавлении, смене порций повторить зависимые расчёты. Не сохранять устаревшие итоги от предыдущего рецепта.

`same`, `medium`, `max` отражают выбранное разнообразие, но точные пределы повторов не заданы. Допуск отклонения от нормы, распределение калорий между приёмами, стартовая дата и поведение при отсутствии перекуса неизвестны. UI-порог предупреждения +10% не является установленным допуском генератора. `BUDGET_TOO_LOW` используется для бюджета, `NO_RECIPES_FOUND` — отсутствия подходящих рецептов; причинная диагностика не должна скрывать аллергию или неизвестные данные.

## 9. Порции, единицы и КБЖУ

### 9.1 Нормализация

Использовать устойчивые productId. Совместимые единицы приводятся к базе: 1 кг = 1000 г, 1 л = 1000 мл. Штуки — отдельная размерность. Граммы и миллилитры не переводятся без достоверной плотности; штуки и граммы — без массы конкретного продукта. Несовместимые количества нельзя складывать или вычитать как одно число. [A/D]

### 9.2 Масштабирование

При базовом числе порций `s0` и выбранном `s` коэффициент `k = s / s0`; количество каждого ингредиента `q = q0 × k`. Соответственно меняются общие КБЖУ и стоимость. Это математическое раскрытие D; значение `s0` для базы должно быть задано, а не угадано.

Переключатели ×0,5 / ×1 / ×2 не должны умножать уже умноженный результат. Число людей, servings в плане и множитель рецепта должны иметь одну согласованную семантику. Не определены дробные штуки, минимальные порции и правила округления Q-05/Q-16.

### 9.3 Расчёт нутриентов

Для каждого ингредиента при количестве `q` в совместимых единицах и данных `Nref` на базовое количество `qref`: `Ningredient = Nref × q / qref`. Сумма ингредиентов даёт КБЖУ рецепта; деление на число порций — КБЖУ порции. Сумма вхождений рецептов с их порциями — итог дня, затем периода. Отображаемое среднее за день должно учитывать действительное число дней; масштаб на человека/семью — Q-04.

Считать ккал, белки, жиры, углеводы по данным продуктов, а не генерировать правдоподобные числа. Не подменять отсутствующие значения нулём. Для ингредиентов в мл/шт нужны нутриенты на соответствующую базу либо подтверждённый перевод. Рецепт и меню обновляют КБЖУ при смене количества, ингредиентов и блюда. План питания не является журналом реально съеденного: факт потребления в P0 не описан, C-08.

Округления должны быть едиными и задокументированными, однако их точность источники не задают. Формулы расчёта персональной нормы, средние нормы по целям и допустимые отклонения не утверждены; медицинские коэффициенты в PRD не добавляются.

## 10. Агрегация, холодильник и покупки

Обязательный порядок D: получить количества всех выбранных блюд → привести совместимые единицы → объединить по ID продукта → вычесть запасы один раз → сгруппировать недостающее для покупки.

Для продукта с известными совместимыми количествами: `required = сумма потребностей`, `covered = min(required, available)`, `purchase = max(0, required − available)`. Покрытие относится ко всему выбранному плану, не повторяется для каждого блюда.

Примеры для тестов A/D:

- Нужно 500 г курицы, дома 200 г: купить 300 г.
- Два блюда требуют 200 и 300 г одного продукта: суммарно 500 г.
- Нужно 1 кг + 500 г риса, дома 300 г: нужно 1500 г, купить 1200 г.
- При запасе больше потребности покупка равна нулю; избыток не становится отрицательной покупкой.

Запись продукта без количества разрешена интерфейсом, но правила её количественного вычета отсутствуют, Q-07. Нельзя автоматически вычитать произвольный или бесконечный объём. Несколько вариантов меню — альтернативы, не одновременное потребление одного запаса; правило активного варианта и источников состояния требует уточнения Q-06.

При изменении блюда, порций или количества запасов потребности, покупки и бюджет пересчитываются согласованно. Пересчёт списка сам по себе не доказывает фактическое расходование запаса. Автосписание, перенос купленного в холодильник, несколько партий и реальные даты годности источниками не определены, Q-10.

## 11. Бюджет и цены

Цены в RUB, по умолчанию оценочные. Для количества `q` и цены `pref` за совместимое базовое количество `qref`: `cost = pref × q / qref`. При отсутствии достоверного значения нельзя выдумывать цену или молча считать её нулевой. [A/D]

Различать:

| Показатель | Смысл |
|---|---|
| Стоимость всех ингредиентов | Оценка полной потребности выбранного меню |
| Покрыто запасами | Оценка той части потребности, которая реально есть дома |
| Требуется купить | Оценка недостающих количеств |
| Остаток бюджета | Лимит минус выбранная база бюджетного контроля |

При одной базе цен и без ручных изменений полная стоимость = покрытие запасами + стоимость покупок. Отметка «куплено» — статус списка, а не доказательство реальной цены чека. Ручные товары могут менять стоимость покупок, но не ингредиенты/КБЖУ меню; правила хранения таких правок не заданы.

Стоимость показывается на меню, дне, порции, ингредиенте и в покупках. Эти значения должны быть выводами одной расчётной модели. Визуальный пример меню 2 870 ₽ и покупок 2 540 ₽ не объясняет разницу сам по себе. База лимита и значения `totalCost` не утверждены Q-04. Упаковки, минимальная единица продажи, скидки, регион, актуализация цен и округление не заданы Q-14/Q-16; учёт потребления по граммам нельзя выдавать за гарантированную сумму кассового чека.
