# Project Research Summary

**Project:** MealPlan  
**Domain:** русскоязычное гостевое веб-приложение планирования питания, домашних запасов и покупок  
**Researched:** 2026-10-25  
**Confidence:** MEDIUM  
**Статус:** синтез исследований для требований и roadmap; рекомендации не закрывают открытые продуктовые C/Q и не подтверждают реализацию.

## Executive Summary

MealPlan должен давать единый проверяемый результат: параметры пользователя превращаются в допустимые варианты меню на 1–7 дней, рецепт и согласованные покупки с количественным учётом запасов. Весь P0-01–P0-16 обязателен, включая разнообразие, 3–4 варианта, пересборку с сохранением предыдущего, редактирование блюд, ручные покупки и PDF. Макеты дополняют подробное frontend-ТЗ, но не повышают функции P1/P2 до P0. Рыночная уникальность и достоверность опроса независимо не проверялись.

Рекомендуется небольшая React/TypeScript SPA с чистым доменным конвейером, одним владельцем исходного состояния, валидируемым локальным хранением и асинхронными mock-адаптерами. Расчёты меню, рецепта, покупок и PDF должны происходить из одного снимка активного варианта. Разрабатывать следует вертикальными срезами: первый гостевой план → изменения плана → домашние запасы → практическая закупка и экспорт → сквозная приёмка. Общие компоненты, доменные тесты и доступность входят в каждый срез.

Главные риски — неопределённые базы бюджета/порций, неподтверждённые пищевые данные, повторный вычет запасов и ложная доказательность отказа генератора. Их нельзя устранить выбором библиотеки: нужны явные решения соответствующих C/Q и проверяемые источники. До закрепления зависимостей требуется проверка опубликованных версий, engines/peers и Safari 15; до приёмки PDF — реальное скачивание и визуальная проверка многостраничного файла с кириллицей. Платные API, аккаунты и сервер не являются зависимостями P0.

## Key Findings

### Recommended Stack

Подробности: [STACK.md](STACK.md). Сохранить предпочтительный стек проекта и минимизировать дополнительные зависимости.

| Технология | Назначение и рекомендация |
|---|---|
| React + strict TypeScript + Vite | SPA, типизированные контракты, локальная разработка и production-сборка; отдельный typecheck обязателен |
| Tailwind CSS, общие CSS tokens | Единая адаптивная система; линия 3.4 — исходный кандидат ради Safari 15, поскольку требования Tailwind 4 к браузеру выше |
| React Router, declarative mode | Маршруты гостевого сценария без серверного framework mode |
| Zustand при подтверждённой необходимости | Один владелец исходного состояния нескольких экранов; хранить исходные данные, а производные вычислять |
| Локальный каталог + runtime-validation + storage adapter | Проверяемые данные, версионированный гостевой снимок и обработка сбоев загрузки/записи |
| html2canvas → jsPDF, ленивый модуль | Предусмотренный PRD путь PDF; отдельный шаблон, единый снимок превью/файла, постраничный рендер |
| Vitest, Playwright, ESLint, TypeScript compiler | Доменные инварианты, браузерные сценарии, фактическое скачивание, типы и качество кода |

**Версионные ворота:** точные номера из STACK являются кандидатами, а не утверждённым lockfile. Перед установкой подтвердить опубликованные releases/registry metadata, совместимость Node/engines/peers и целевых браузеров. `package.json` ветки `main` и шаблон репозитория сами по себе не доказывают опубликованную версию. Не обходить конфликты через force/legacy-peer-deps. Проверить build target и используемые Web API: транспиляция JavaScript не добавляет все polyfills. Современный Playwright WebKit не подтверждает именно iOS Safari 15.

TanStack Query, IndexedDB, solver/Worker и Firebase добавлять только при реальной необходимости и в разрешённом объёме. Для первого P0 не нужны облако, аутентификация или LLM.

### Expected Features

Подробности: [FEATURES.md](FEATURES.md). Базовые и отличительные возможности ниже — вывод из задач MealPlan, а не утверждение о конкурентах.

**Обязательные P0:**

- Гостевые маршруты, приветствие, быстрый старт и четырёхшаговый мастер с восстановлением черновика.
- Люди 1–10, дни 1–7, бюджет, цель/КБЖУ в пределах разрешённых правил, время, ограничения, запасы и разнообразие.
- Детерминированная генерация с отменой, повтором, таймаутом и объяснимым отказом; 3–4 варианта и сохраняемая пересборка.
- Меню день/неделя, сводки, рецепт, порции ×0,5/×1/×2, замена из допустимых альтернатив, удаление и добавление в пустой слот.
- Полная стоимость ингредиентов, стоимость покрытия запасами и оценка закупки как отдельные показатели; единый пересчёт после изменений.
- Количественный холодильник, expiresSoon, генерация из остатков; агрегация покупок по ID и совместимым единицам, однократное покрытие запасами.
- Категории/табы, источники блюд, ручные товары и правки, отметки, фильтр/сброс, текстовый обмен и fallback; PDF с превью и опциями.
- Русский UI/RUB, loading/empty/error, доступность и адаптивность на 360/390/430/768/1280 px.

**Отличительная ценность уже внутри P0:** количественная связь меню–запасы–покупки–бюджет; сравнение вариантов без потери результата; честный отказ при недопустимых ограничениях; актуальный печатный список. Эти функции нельзя отложить как необязательные улучшения.

**Отложить:** P1 только после всей приёмки P0 — PNG, готовка, профиль/норма в его разрешённом объёме, избранное, история/графики, каталог и поиск рецептов, дополнительные pantry-функции, настроенная авторизация. C-04 о калькуляторе внутри мастера остаётся открытым. P2 только по запросу — realtime-семья, статистика экономии, персонаж, drag-and-drop, собственные рецепты, сохранённые приёмы, штрихкоды. Доставка, акции и КБЖУ по фотографии исключены исходным ТЗ.

### Architecture Approach

Подробности: [ARCHITECTURE.md](ARCHITECTURE.md). Рекомендуется один чистый конвейер:

```text
валидированные настройки + активный вариант + каталог + pantry
 → порции конкретного вхождения → ингредиенты и КБЖУ
 → агрегация потребности всего периода по productId и размерности
 → однократное покрытие запасами → недостающие покупки
 → три стоимости и проверка согласованной базы лимита
 → единая проекция для меню, рецепта, покупок и PDF
```

1. **Domain:** единицы, масштаб от исходного выхода рецепта, нутриенты, цены, ограничения, подбор, потребности и pantry; без React/DOM/storage.
2. **Application/state:** команды, активный вариант, адресация по ID вхождения блюда, ревизии, отмена, подтверждение/откат и производные проекции.
3. **API/storage adapters:** валидируемые асинхронные контракты, реальные доменные операции в mock, версионированное сохранение исходного снимка и восстановимые ошибки.
4. **UI/export:** представление проекций, доступные действия и состояния; PDF не выполняет отдельный вычет запасов или расчёт бюджета.

Не сохранять независимые итоги каждого экрана. Переключение вариантов и вычисление покрытия не расходуют pantry. Ручные правки покупок отделить от вычисленной потребности; конкретная политика их сохранения остаётся Q-09. Неполные данные не превращать в ноль или доказанную безопасность.

### Critical Pitfalls

Подробности: [PITFALLS.md](PITFALLS.md).

1. **Несогласованные базы денег и питания.** До приёмки решить период/базу лимита, семейный масштаб, базовый выход и округление; проверять три стоимости и отсутствие двойного масштабирования.
2. **Повторное покрытие запасами и ложные конверсии.** Сначала агрегировать активный план, затем вычитать запас один раз; неизвестное количество явно отличать от известного, г↔мл↔шт переводить только по проверенному коэффициенту.
3. **Недостоверные данные и ложный отказ поиска.** Не ослаблять аллергии; проверять ингредиенты и полноту сведений. Различать таймаут, неполные данные и доказанную невозможность; не выдумывать минимальный бюджет и уникальные варианты.
4. **Протекание правок между вариантами и потеря покупок.** Адресовать вхождение, применять согласованный снимок и откат; проверить повтор recipeId, A→B→A, поздний ответ после отмены и ручные правки после пересчёта.
5. **Формальная готовность PDF/мобильного UI и расползание scope.** Проверять скачанный файл, шрифты и целые строки A4, размеры/фокус/ошибки и целевой Safari. Не заменять весь P0 красивыми экранами или ранним P1.

## Implications for Roadmap

Ниже предложены пять вертикальных срезов. Это рекомендация структуры, не утверждённые продуктовые решения. Первый срез включает минимальный каркас и расчётные контракты вместе с работающим пользовательским путём; отдельную фазу «весь фундамент без сценария» не создавать.

### Phase 1: Получить первый гостевой план

**Rationale:** сразу проверить core value, модель вариантов и весь расчётный конвейер на минимальном UI.  
**Delivers:** приветствие/быстрый старт → четыре шага с reload → реальный подбор → 3–4 варианта и пересборка → меню день/неделя → рецепт и базовые рассчитанные покупки. Уже учитываются известные запасы, ограничения, дни и разнообразие. Минимальные доступные компоненты и состояния создаются здесь.  
**Addresses:** P0-01–08; базовый путь P0-10/11/15/16.  
**Avoids:** фиктивная генерация, одновариантная модель, выдуманная норма/цены, потеря ограничений.  
**Gates:** Q-01–06/Q-08/Q-11/Q-14–17 и C-04/C-06 в зависимом объёме; опубликованные версии, Safari 15 и проверяемые данные. Исследовать генератор/каталог, провести ранний PDF spike, не объявляя экспорт готовым.

### Phase 2: Изменить блюдо и увидеть согласованный результат

**Rationale:** строится на активном варианте и проверяет устойчивость расчётов при мутациях.  
**Delivers:** 3–5 допустимых альтернатив с дельтами, замена/удаление/заполнение слота, полный рецепт и масштабирование; немедленно согласованные меню, КБЖУ, стоимость и базовые покупки, обработка ошибки/отката.  
**Addresses:** P0-09/10, развитие P0-07/08/11/15/16.  
**Avoids:** двойной масштаб, изменение всех повторов recipeId, устаревший ответ и несогласованный откат.  
**Gates:** Q-04–06/Q-08/Q-16; правила выхода за лимит и применения порций должны иметь основание.

### Phase 3: Использовать домашние продукты и уменьшить закупку

**Rationale:** базовое покрытие уже работает; теперь проверяется полный пользовательский жизненный цикл запасов.  
**Delivers:** поиск/добавление/правка/удаление, количества, expiresSoon, генерация из остатков, связь мастера с холодильником, обновление покупок и трёх стоимостей.  
**Addresses:** P0-13; завершение pantry-частей P0-04/08/11/15, сквозной P0-16.  
**Avoids:** бесконечный неизвестный запас, повторный вычет, скрытая устарелость и автоматическое списание без требования.  
**Gates:** C-03; Q-07/Q-10/Q-11. Принять явное поведение «Пересчитать / Позже» и неизвестных количеств.

### Phase 4: Собрать покупки и скачать читаемый PDF

**Rationale:** ручные действия и экспорт опираются на согласованную закупку предыдущих срезов.  
**Delivers:** группы/табы/источники блюд, «Уже есть дома», отметки/фильтр/сброс, ручные товары и количества, удаление, текстовый обмен с fallback; превью/опции и реальный A4 PDF с кириллицей, целыми строками и несколькими страницами.  
**Addresses:** завершение P0-11; P0-12/14 и связанные P0-15/16.  
**Avoids:** потеря ручных правок при пересчёте, расхождение превью/файла, пустой или обрезанный экспорт.  
**Gates:** Q-06/Q-09/Q-12/Q-13/Q-17; проверить PDF на фактических ресурсах и длинном списке.

### Phase 5: Подтвердить весь P0 сквозными сценариями

**Rationale:** локальная готовность срезов не доказывает их совместимость; эта фаза завершает приёмку, а не откладывает все проверки до конца.  
**Delivers:** трассировка и фактически выполненная проверка всех AC-01–AC-18, исправления интеграционных дефектов, валидация качества каталога, reload/ошибки/отмена, доступность и адаптивность на пяти размерах. Vitest, Playwright, typecheck, ESLint и production build с записанными результатами.  
**Addresses:** окончательная приёмка P0-01–16, особенно P0-15/16.  
**Avoids:** объявление P0 готовым по скриншотам, mock-каталогу или непроведённым браузерным тестам.  
**Gates:** зависимые открытые C/Q разрешены; недоступная проверка именно Safari 15 явно отмечена, современный WebKit её не заменяет. P1 не начинать до удовлетворения P0.

### Phase Ordering Rationale

- Варианты, базовые покупки и pantry-покрытие входят в первый срез, иначе позднее изменятся контракты генератора и хранения.
- Мутации проверяются до расширения списка покупок; ручные правки требуют уже стабильного пересчёта.
- PDF завершает рабочий путь, но технический риск кириллицы/пагинации проверяется рано.
- Покрытие P0: 01–08 — фаза 1; 09–10 — фаза 2; 11 — фазы 1/3/4; 12 — фаза 4; 13 — фаза 3; 14 — фаза 4; 15–16 — все срезы и итоговая фаза 5. Roadmapper должен разложить это в атомарные требования без потерь.

### Research Flags

**Нужна углублённая проработка при планировании:** фаза 1 — C-04/формулы, данные, budget/portion policies, детерминированный подбор, достаточность вариантов, версии/Safari; фаза 2 — альтернативы и дельты при pantry/лимите; фаза 3 — C-03 и unknown-политика; фаза 4 — семантика ручных правок и экспортный состав, PDF spike. Для них уместен `$gsd-plan-phase --research-phase <N>` в относящемся объёме.

**Стандартные паттерны после разрешения ворот:** маршрутизация, формы, общие компоненты, версии локального снимка, чистые арифметические функции и стандартный QA-процесс фазы 5. Отдельное внешнее исследование этих частей не требуется без нового неизвестного API или фактического сбоя.

### Gaps to Address

- **Q-01/Q-03–05/Q-16, C-04:** период/лимит, норма, семейные КБЖУ, базовые порции и округление — до приёмки зависимых расчётов. Примеры макетов не заменяют решение.
- **Q-06/Q-08:** уникальность/нехватка вариантов и альтернатив, разнообразие, накопление, причины отказов — проверить на небольших исчерпываемых наборах и достаточном каталоге.
- **Q-14:** источники нутриентов, аллергенов/ограничений, оценочных цен, 50+ рецептов и прав на ресурсы. 10–15 mock-рецептов не доказывают достоверность продукта или разнообразие.
- **C-03/Q-07/Q-09–13:** unknown pantry, актуальность, ручные правки/отметки/категории и экспортный набор — явные ворота соответствующих сценариев.
- **Q-02/Q-11/Q-15/Q-17, C-06:** крайние значения/пропуск, хранение и восстановление, временная навигация профиля, финальные ресурсы и условия performance QA.
- **Версии и браузеры:** подтвердить опубликованные совместимые зависимости и цель Safari 15 до закрепления стека; доступность целевого устройства/браузера остаётся проверочным ограничением.
- **P1/P2 и Q-18:** сохранить вне текущего исполнения; исследование не разрешает дальнейший релиз автоматически.
