# Roadmap: MealPlan

## Overview

Пользователь сохраняет гостевые настройки, получает допустимое меню на 1–7 дней и рассчитанные покупки, сравнивает варианты, меняет блюда и порции, уточняет запасы и собирает закупку с PDF. Фазы расширяют работающие пользовательские сценарии; общие компоненты, чистые доменные функции и проверки создаются вместе с ними. Дорожная карта описывает будущую реализацию: код, браузерные проверки и сборка ещё не выполнены.

## Milestones

- 🚧 **v1.0 P0 MVP** — фазы 1–7, весь P0-01–P0-16 и AC-01–AC-18.
- P1 / NEXT-01–NEXT-10 отложены до приёмки всего P0; их фазы сейчас не планируются. NEXT-10 — перенесённая вычислительная часть прежнего WIZ-09 по подтверждённой поправке C-04 от 26.10.2026. P2 требует отдельного запроса.

**Project mode:** mvp. **Granularity:** standard. **Phase ID convention:** sequential. Режим MVP не уменьшает согласованный P0: варианты, разнообразие, пересборка, ручные покупки и PDF обязательны.

## Phases

- [ ] **Phase 1: Гостевой старт и сохраняемые настройки** - Пользователь проходит мастер и сохраняет параметры будущего плана.
- [ ] **Phase 2: Первый допустимый план и рассчитанные покупки** - Пользователь получает реальное меню, прозрачные КБЖУ, бюджет и недостающие продукты.
- [ ] **Phase 3: Сравнение вариантов и просмотр рецептов** - Пользователь выбирает вариант, пересобирает меню и изучает блюда без потери состояния.
- [ ] **Phase 4: Изменение блюд и порций** - Пользователь редактирует конкретное блюдо и сразу получает согласованные итоги.
- [ ] **Phase 5: Домашние запасы и меню из остатков** - Пользователь управляет холодильником и видит его количественное влияние на закупку.
- [ ] **Phase 6: Покупки в магазине** - Пользователь редактирует, отмечает и передаёт актуальный список покупок.
- [ ] **Phase 7: PDF и завершённый сквозной P0** - Пользователь скачивает читаемый документ и проходит весь согласованный сценарий на целевых экранах.

## Phase Details

### Phase 1: Гостевой старт и сохраняемые настройки

**Goal:** Пользователь без регистрации открывает P0-разделы и сохраняет валидные параметры питания в четырёхшаговом мастере.
**Mode:** mvp
**Depends on:** Nothing (first phase)
**Requirements:** APP-01, APP-02, APP-03, WIZ-01, WIZ-02, WIZ-03, WIZ-04, WIZ-05, WIZ-06, WIZ-07, WIZ-09, UX-01
**Success Criteria:**
1. Пользователь открывает P0-маршруты гостем, видит приветствие и переход в мастер; существующий план ведёт с `/` на `/menu`. Нижняя навигация телефона и боковая от 1200 px следуют решённому C-06, мастер полноэкранный.
2. Пользователь проходит четыре шага с прогрессом, возвращается назад и восстанавливает черновик после перезагрузки; выход с первого заполненного шага требует подтверждения.
3. Пользователь выбирает 1–10 человек, 1–7 дней на шаге 1, цель, время и разнообразие; поле и слайдер бюджета синхронны, подсказка на человека в день и крайние значения соответствуют решениям Q-01/Q-02.
4. Пользователь вводит ограничения и теги исключений, ищет домашние продукты, задаёт необязательные количества и флаг скорого истечения; по желанию задаёт ручную цель КБЖУ на человека в день с происхождением «Введено вручную». Пустая цель допустима, частичная требует исправления/очистки; средние значения не подставляются. Автокалькулятор и его четыре состояния перенесены в P1/NEXT-10 по human-confirmed C-04; WIZ-09 принимается только по обновлённому ручному контракту, вычисление не объявляется выполненным.

### Phase 2: Первый допустимый план и рассчитанные покупки

**Goal:** Пользователь получает допустимый план выбранного периода и проверяемые расчёты меню и закупки через локальные адаптеры.
**Mode:** mvp
**Depends on:** Phase 1
**Requirements:** APP-04, WIZ-08, DATA-01, DATA-02, DATA-03, CALC-01, CALC-03, CALC-04, CALC-05, CALC-06, CALC-07, GEN-01, GEN-02, GEN-03, GEN-04, GEN-05, MENU-01, MENU-04, SHOP-01, SHOP-04
**Success Criteria:**
1. Пользователь действительно запускает генерацию из мастера либо «Меню за 1 клик» с последними/согласованными настройками; пропуск шагов 3/4 обрабатывает сохранённые ограничения и запасы по Q-11.
2. Пользователь получает воспроизводимое меню выбранных дней и людей с учётом бюджета, нормы, времени, разнообразия и запасов. Аллергии/исключения соблюдены; продукты имеют стабильные ID, проверяемые базы цены/КБЖУ и выход рецепта, а неизвестные данные не становятся нулём или подтверждением безопасности. Платный API для этого не требуется.
3. Пользователь видит процесс генерации, отменяет его без применения позднего ответа, повторяет ошибку или таймаут 30 секунд и возвращается к сохранённым параметрам; бюджетный отказ ведёт на шаг бюджета, обоснованный минимум не подменяется догадкой.
4. Пользователь видит даты, средние ккал относительно нормы, дневные Ккал/Б/Ж/У, текстовое предупреждение свыше нормы на 10%, лимит/остаток и три отдельные стоимости: ингредиенты, покрытие запасами, закупка. Масштаб человека/семьи, период лимита и округление явны и согласованы; цены обозначены как оценки.
5. Пользователь открывает базовые покупки с источниками блюд и блоком «Уже есть дома»: совместимые количества агрегированы по ID, запас вычтен один раз для всего плана, например 500 г − 200 г = 300 г; несовместимые единицы не смешаны, отрицательных покупок нет.

### Phase 3: Сравнение вариантов и просмотр рецептов

**Goal:** Пользователь сравнивает меню, сохраняет предыдущие варианты и изучает рецепты из согласованного состояния приложения.
**Mode:** mvp
**Depends on:** Phase 2
**Requirements:** DATA-04, GEN-06, GEN-07, MENU-02, MENU-03, REC-01, REC-02, REC-04
**Success Criteria:**
1. Пользователь получает предусмотренные 3–4 варианта, сравнивает их стоимость и выбирает активный; при нехватке допустимых вариантов видит результат по Q-06 без фиктивных различий. Покупки соответствуют выбранному варианту.
2. Пользователь пересобирает меню с теми же настройками и возвращается к предыдущему для сравнения; пересоздание с потерей данных требует подтверждения, накопление вариантов следует Q-06.
3. Пользователь переключает день/неделю и дни на телефоне, видит сегодняшний день и настольную сетку четырёх типов приёмов. Карточки показывают фото 4:3, тип, время, ккал, цену порции, признак запасов и открывают нужный рецепт.
4. Пользователь читает ингредиенты с ценами и отметками запасов, нумерованные шаги, четыре КБЖУ порции и вклад ингредиентов; неизвестный ID показывает «Такого рецепта нет» и возврат к меню.
5. После перезагрузки пользователь получает валидированное согласованное состояние активного варианта; повреждённые данные и сбои сохранения дают явную ошибку/восстановление, а не ложное подтверждение записи.

### Phase 4: Изменение блюд и порций

**Goal:** Пользователь меняет конкретное вхождение блюда без рассогласования меню, питания, бюджета и покупок.
**Mode:** mvp
**Depends on:** Phase 3
**Requirements:** CALC-02, MEAL-01, MEAL-02, MEAL-03, REC-03
**Success Criteria:**
1. Пользователь выбирает замену в bottom sheet из 3–5 допустимых альтернатив с дельтой цены/ккал; нехватка кандидатов и выход за лимит обрабатываются явно по Q-08.
2. Пользователь убирает блюдо и заполняет освободившийся слот через «+ Добавить блюдо» с теми же действующими ограничениями.
3. Пользователь применяет ×0,5/×1/×2 к выбранному вхождению рецепта, видит согласованные ингредиенты, КБЖУ и цену без повторного умножения и может вызвать замену из рецепта; повтор этого recipeId в другой день не меняется случайно.
4. После замены, удаления, добавления или изменения порций пользователь сразу видит обновлённые итоги активного плана и покупки; ошибка подтверждения не оставляет ложный успешный результат или устаревшие суммы.

### Phase 5: Домашние запасы и меню из остатков

**Goal:** Пользователь управляет продуктами дома и видит количественно правильное влияние запасов на план и закупку.
**Mode:** mvp
**Depends on:** Phase 4
**Requirements:** GEN-08, HOME-01, HOME-02, HOME-03
**Success Criteria:**
1. Пользователь ищет и добавляет продукт в `/pantry`, использует популярные чипы, меняет количество, флаг «Скоро испортится» и удаляет запись.
2. Пользователь видит покрытую и недостающую часть потребности; запись без количества обрабатывается по Q-07 и не становится бесконечным запасом.
3. После правки запасов пользователь получает актуальные покупки и стоимость и согласованное действие «Пересчитать / Позже» по C-03; устаревший результат не выдаётся за актуальный, связь холодильника с мастером следует Q-11.
4. Пользователь запускает меню из остатков; при возможности скоро портящиеся продукты получают приоритет первых 1–2 дней, без ослабления пищевых ограничений и повторного расходования одного запаса при переключении вариантов.

### Phase 6: Покупки в магазине

**Goal:** Пользователь собирает закупку по отделам, вносит ручные изменения и передаёт актуальный список.
**Mode:** mvp
**Depends on:** Phase 5
**Requirements:** SHOP-02, SHOP-03, SHOP-05, SHOP-06, SHOP-07, SHOP-08
**Success Criteria:**
1. Пользователь сворачивает группы по отделам и фильтрует товары табами с иконками; группы и подкатегории соответствуют разрешённому Q-12.
2. Пользователь отмечает купленное: строка зачёркивается и уходит вниз группы, счётчики/прогресс обновляются; фильтр скрывает купленное, сброс возвращает отметки в исходное состояние.
3. Пользователь добавляет ручной товар с названием, количеством и отделом, меняет количество и удаляет строку. После смены блюда/порций/запасов/варианта ручные правки, отметки и оценка суммы следуют Q-09, а ингредиенты и КБЖУ меню не подменяются ручным списком.
4. Пользователь передаёт текст через Web Share или копирует его при отсутствии поддержки; сбой и резервное действие видны.
5. Пользователь видит согласованные число товаров и оценку суммы, осмысленное состояние без меню и состояние «всё куплено» с переходом к новому меню.

### Phase 7: PDF и завершённый сквозной P0

**Goal:** Пользователь скачивает актуальный читаемый PDF и надёжно проходит весь P0 от настроек до закупки на целевых устройствах.
**Mode:** mvp
**Depends on:** Phase 6
**Requirements:** MENU-05, PDF-01, PDF-02, PDF-03, PDF-04, PDF-05, UX-02, UX-03, UX-04
**Success Criteria:**
1. Пользователь переходит из меню к настройкам, пересозданию, покупкам со счётчиком и экспорту; в PDF-модалке меняет группировку, цены, количества и пустые чекбоксы, видит живое превью и действительно скачивает A4 portrait из того же актуального снимка с согласованными датой, логотипом, суммой и составом.
2. Пользователь читает русский многостраничный PDF с категориями/иконками и чекбоксами: кириллица, шрифты и изображения сохранены, строки товаров не разорваны страницами, выбранные опции соблюдены.
3. Пользователь видит загрузку экспорта и «Не удалось создать файл. Повторить» при сбое; во всём P0 доступны применимые loading/empty/error и восстановление, потерю данных можно подтвердить/отменить, включая отмену тостом 5 секунд там, где она выбрана.
4. Пользователь завершает P0 на 360/390/430/768/1280 px без горизонтального скролла страницы и перекрытий, с клавиатурой, видимым фокусом, контрастом AA, целями ≥44×44 px и основными кнопками ≥48 px.
5. Пользователь проходит согласованный путь настройки → варианты → замена/порции → запасы → ручные покупки → PDF без блокирующих регрессий; готовность подтверждена фактически выполненными Vitest, Playwright, typecheck, ESLint, production build и просмотром скачанного PDF по AC-01–AC-18. Непроведённые проверки браузеров/LCP и ограничения данных указаны явно.

## Delivery Conventions

В каждой фазе использовать существующие [AGENTS.md](../AGENTS.md) и [mealplan-domain](../.agents/skills/mealplan-domain/SKILL.md); доменные функции отдельно от React, стабильные ID, одна проекция активного плана, валидируемые адаптеры. UI строится по PDF с общими токенами/компонентами; UI UX Pro Max, Vercel React Best Practices и Web Design Guidelines применяются к соответствующей работе. Версионные API проверяются по актуальной официальной документации до использования.

Релевантные Vitest и браузерные сценарии, TypeScript, ESLint и production build входят в готовность каждой реализуемой фазы. Superpowers применяется для TDD доменной логики, отладки, review и проверки перед заявлением о завершении. Phase 7 не переносит эти обязанности на конец проекта. Неизвестные источники пищи/цен, непроведённые браузерные проверки и нерешённые критические ворота не допускают заявления о готовности зависимых функций.
